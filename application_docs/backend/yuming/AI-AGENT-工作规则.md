# AI Agent 工作规则

**这份是给 AI（Codex / Claude / 其它）看的操作规则，不是给人看的说明文档。**

要理解这套系统怎么跑，读同目录的 `Cadensy-AI-系统地图.md`。
这份只回答一件事：**在这个领域里工作，什么能做、什么不能做、改完必须验什么。**

仓库根目录的 `AGENTS.md` 讲的是前端架构边界（导航、会话、Plan 交互），
和这份互不重叠，两份都要遵守各自的范围。

## 1. 三条不可越过的线

违反任何一条，改动直接作废，不讨论。

### 1.1 工具永远只读

`agents/tools.py` 里的工具**不能写数据库**。agent 只能「查」和「判定」，
真正的改动必须由用户在界面上点 Apply 才提交。

新增工具时必须有测试证明它不写库（参考 `test_tools_do_not_write_decision_or_plan_tables`）。

### 1.2 决策路径由 Python 定，AI 只能服从

`notice` / `round` / `reopen_round` / `confirm` 由
`domain/constraints/engine.py · classify()` 决定。

- 模型**不能**自己选路径
- 模型只能调 `classify_change`，然后按返回结果说话
- 系统提示词里那条「Do not choose a decision path yourself」不许删

### 1.3 `unknown` 永远不等于假默认值

价格、时长、营业时间、步行量未知时**留空**，不要填 `0`、`90 分钟`、`免费`。

下游必须显式处理 `None`（跳过、或明确说明未知），
不许为了让逻辑跑通而在数据层塞一个假的默认值。

## 2. 改之前必须知道的四件事

### 2.1 系统提示词只有一份

定义在 `domain/chat/service.py · _agent_system_prompt()`。

验证脚本 `agents/agent-server/run_real_trip_tools_trace.py` **从这里导入**。

历史教训：脚本曾经自带一份副本，两边各自演进后互相缺失规则，
导致「脚本跑通了」不代表线上行为正确。**不要再复制这段提示词。**

### 2.2 工具描述就是行为

模型靠 `description` 决定「调哪个工具、传什么参数」。

**描述写错不会报错**，只会让模型在某个没测到的场景里悄悄调错工具。
所以改描述属于行为变更，必须走第 4 节的验证流程。

### 2.3 前端传上来的一切都不可信

任何从 HTTP 请求体进入的 patch、选项、id，都必须在后端重新校验：

- id 必须属于**当前这个 trip**（只查「存在」不够，可以跨行程注入）
- 字段必须在白名单内
- 数值必须在合理范围内
- 最终要能通过 `classify()`

尤其注意：能进入 `decision_round.options` 的东西，
投票通过后会被 `settle_round` **写进真实行程**。

### 2.4 选项没有 patch 就等于不改

结算时只有 `split` 允许用选项标题当改动内容（它靠改标题实现并行展示）。
其它没带 patch 的选项一律视为不改。

**不要恢复「拿 option['title'] 当 patch」的兜底**——
那会把 UI 文案写成行程条目的名字。

## 3. 已知的坑（都踩过一次）

| 坑 | 症状 | 正确做法 |
|---|---|---|
| `day_date` 传字符串给判定层 | 事务被中止，**后续所有查询全崩** | 判定层要真正的 `date` 对象；JSON 边界上才用 ISO 字符串 |
| 用 `except Exception` 吞掉数据库错误 | 异常没了但事务已废 | 用 `db.begin_nested()` savepoint 隔离每次试探性校验 |
| 只查 `PlanItem` 存在 | 可跨行程注入 | 必须确认它属于当前 plan / trip |
| 只校验「属于当前 trip」 | **同 trip 的另一个条目也能通过**，但结算时会写到 round 自己的条目上 | 必须就是**被改动的那一个**条目 |
| 单次真实验证就下结论 | 结论不可靠 | 同一配置跑 3 次看中位数 |
| 城市名精确匹配 | 填 "LA" 查不到 "Los Angeles" 的缓存，行程 blocked | 改之前先确认目的地字符串怎么归一化的 |

---

### 3.1 安全要求要按「执行时会作用到谁」写

上表最后一条是真实发生过的：prompt 里写的是「必须属于当前 trip」，
实现照做了，测试也过了，**但漏掉了更近的那条边界**——
同一个 trip 里的另一个条目同样能通过校验。

后果是：拿条目 A 校验、投票通过后写到条目 B 上。
**校验通过、测试全绿、日志完全正常**，只有真正投票落地时才会发现。

写安全要求时不要问「这个数据属于谁」，要问
**「如果它赢了，最终会被写到哪个对象上」**，然后校验那个对象。

## 4. 验证流程（顺序不能反）

> **单元测试全绿不代表 agent 调对了。**
> 测试只保证你没把别的东西碰坏。

### 第一步：真实验证

**触发条件：改了工具描述、工具返回字段、系统提示词、工具签名。**

```bash
cd backend
MOCK_AI=0 DISABLE_SCHEDULER=1 .venv/bin/python \
  app/agents/agent-server/run_real_trip_tools_trace.py
```

只看结尾的 `=== Summary ===`，记录每个场景的**轮数**和**工具顺序**。

**必须跑 3 次，报中位数。** 同样的代码两次跑出不同轮数是常态。

判断标准：

- 轮数变少 → 通常是好的，模型少犹豫了
- **轮数明显变多，或该调的工具不调了 → 改坏了，退回去**
- 简单问答那两个场景（「周三下午有什么安排」「介绍一下 Art Institute」）
  应该稳定在 **2 轮**。变成 3 轮以上说明新东西让模型犹豫了

脚本在测试库的一个事务里造临时行程，跑完回滚，不落盘。

### 第二步：单元测试

```bash
cd backend
DISABLE_SCHEDULER=1 MOCK_AI=1 .venv/bin/python -m pytest -q -p no:cacheprovider
```

要求全绿。

### 第三步：日志核对（排查时用）

```bash
cd backend
tail -f logs/agent-trace-$(date +%Y%m%d).jsonl    # 每一轮调了哪个工具
tail -f logs/trace-$(date +%Y%m%d).jsonl          # 每次模型调用：路由/供应商/耗时/token
```

判断「这句话到底有没有走到 agent」看第一个；
判断「到底有没有真的调 AI」看第二个。

## 5. 写测试的要求

**新行为必须有测试，而且这条测试要能在改动前失败。**

历史教训：今天修好的两个 bug——「单人行程也要投票」和
「空选项会把行程改名」——**修复前后测试数量一样、全都通过**，
因为那两条路径从来没被测过。测试没坏不等于没问题。

必须覆盖的类别：

- **安全边界**：跨 trip 注入、字段白名单、只读保证
- **降级路径**：超时、报错、空回复各自的行为
- **回归保护**：不传新参数时行为和以前完全一致
- **隐私**：工具返回里不得出现成员 id、姓名、私密约束原文
  （参考 `test_tool_outputs_do_not_expose_member_identity_or_private_preference_text`）

---

## 6. 不要做的事

- 不要为了让测试通过而放宽安全校验
- 不要在写路径（提交改动、开投票、结算）里调用 AI
  ——那是事务性请求，AI 超时会让整个提交失败
- 不要让投票选项实时生成
  ——一场投票开 24 小时，全组必须看到同一组选项
- 不要复制系统提示词
- 不要在 `agents/` 里重新实现 `domain/` 已有的规则
- 不要删掉安全闸 `_claims_change_completed`
  ——它拦截模型宣称「改动已生效」，是产品前提的最后一道防线
- 不要 commit，除非明确要求
- 不要碰 `docs/yuming/`

## 7. 交活时必须说清楚

1. 改了哪些文件，为什么
2. 真实验证的**前后对比**：每个场景的轮数和工具顺序，3 次中位数
3. 新增了哪些测试，分别保护什么
4. **哪些地方你选择不改，为什么**
5. 遇到的意外和你的判断依据

**不要只报「测试全绿」。** 那是最低要求，不是结论。
